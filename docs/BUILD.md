## The source tree

```
firmware/src/frodhes.c    <- the app: keys, MIDI, sustain, settings, the main loop
firmware/src/rhodes.c     <- the voice engine: tine and tonebar, hammer, pickup, damper
firmware/src/bars.c       <- the bar instruments (VIBES, MARIMBA): bar modes, tube, mallet, damper / hand, motor
firmware/src/fx.c         <- the effects and the master (limiter, silence gate)
firmware/src/keyvel.c     <- key velocity: a key's reading once it lands -> its velocity (TOUCH); hal/fm1_keyadc.h the rows
firmware/src/ui.c         <- the pages;  params.c the parameters;  tempo.c tempo and scales;  presets.c
firmware/gen/             <- tables generated by tools/gen_rhodes.py, tools/gen_bars.py and tools/gen_fx_tables.py
firmware/src/platform.c   <- Dinghy's plumbing (boot, USB, updates, audio ISR, settings)
```

The app is one compilation unit: `frodhes.c` includes `platform.c`, then the engine, the effects and the UI.
[API.md](API.md) describes what the platform provides; [RULES.md](RULES.md) lists the chip's rules (no FPU, no 64-bit
division, a 5.8 ms audio budget per 256 frames) and the checks the build runs.

## Build

You need Python 3, JieLi's toolchain and the JieLi AC79 SDK; on macOS also Docker (the toolchain is Linux x86-64
only). Everything installs inside the project, in `.local/` (git-ignored):

```sh
make setup        # .local/venv, the JieLi toolchain, the AC79 SDK files (sha256-checked)
./build.sh        # build/frodhes.fwsc;  ./build.sh --release X.Y.Z -> build/frodhes-X.Y.Z.fwsc
```

Every build, release or not, has the package identity `FM-1_958`; the version is only text on the screen and in the
file name.

## Tests on the computer

```sh
make test         # the host scripts in tests/scripts
make pytest       # the Python tests (generators, the C engine against its reference, effects); in parallel
                  # with pytest-xdist (PYTEST_N=auto; PYTEST_N=0 or no xdist: serial)
make host         # render build/host/frodhes.wav and screen PNGs on the computer, no FM-1 needed
```

`tools/cpu_budget.py` predicts the audio interrupt's worst block on the computer from the FM-1's measured costs.

`tools/manual_shots.py` renders the manual's screenshots and sets each picture link's `?v=` to the file's hash. After
editing a picture by hand, run `tools/doc_links.py --fix`. A test fails if a screenshot or a link is stale. The
README's social preview picture is ![the start screen](manual/img/thumbnail.png?v=23c51997)
(`docs/manual/img/thumbnail.png`, made by the same tool).

## Tests on the FM-1

These tools play the FM-1 over USB-MIDI and analyse its USB audio:

- `tools/hil_scan.py`: keys, velocity, every effect, presets.
- `tools/hil_jack.py`: compares the headphone jack, recorded with an audio interface, against the USB audio.
- `tools/hil_usb_onset.py`: every note reaches the USB recording as soon as the jack, after a knob turn and a pause
  too (the settings save lands there).
- `tools/rc_gate.sh VERSION PREV_FWSC [--from STEP] [--only STEPS] [--dry-run]`: the release candidate's device
  queue in one DEVICE hold: install, T1, crackle at 44.1 and 48 kHz, hil_cpu and `--worst` x3 per engine, the
  monkey 4 x 20 min, T1's S3 3 more times, T2, hil_autosave; each step's log and exit code in
  build/rc-VERSION/.
- `tools/hil_autosave.py`: lets the settings save land while a computer records, and checks that the USB stream stays
  clean (missed 0, overruns 0) and the flash write's longest interrupts-off stretch.
- `tools/hil_clock.py`: sends MIDI clock (over USB-MIDI, or `--via trs --port NAME` from a MIDI interface into the
  TRS IN) and checks that every synced item follows it: the tremolo, phaser, chorus, filter LFO and VIBES motor by
  their effect on the audio, the delay types' echoes, the arpeggiator and the sequencer on the 1/16 grid. It runs
  through a tempo change and a Stop / Start, with CLOCK INT too (`--via int`), and writes one table row
  | INT | EXT-USB | EXT-TRS (`--selftest`, `--dry-run` without the FM-1).
- `tools/hil_cpu.py`: the audio interrupt's worst block and the USB audio's health (`--usb 44100|48000` holds a
  DAW-like stream open).

## The browser emulator

`web/build.sh` builds the browser emulator (Emscripten; `web/web_hal.c` stands in for the hardware) into `web/dist/`.
The page shows the version it was built with (`web/build.sh --release X.Y.Z`, else `dev`). CI builds it and runs its
selftest (Chromium and WebKit) on every pull request.

## Releases

Releases are one command:

```sh
tools/release.py [patch|minor|X.Y.Z] [--dry-run] [--no-device [--device-done FILE]] [--full] [--no-emulator] [--yes]
```

It stops at the first failure and ends with a table of every step (done, skipped and why, failed). In order, it:

1. picks the next version from the latest tag;
2. checks the tree: on `main`, clean, not behind `origin/main`, the release-note fragments in `docs/changes/` well
   formed (`tools/changes.py`);
3. runs the host tests and the release build;
4. installs the build on the FM-1 and runs the tiers the change needs (`tools/test_map.py` maps every file to them):
   - on every release, the must-pass scenarios (`tools/hil_scan.py --tier must`): six real-use scenarios judged by
     the firmware's own CC 116 counters and the audio;
   - only when an engine or the DSP changed, or with `--full`: the full sound scan, and the CPU, scan and jack tests
     on the Rhodes, VIBES and MARIMBA (and the MARIMBA sample-back);
   - `--device-done FILE` records FM-1 runs already made on the same build, checked by its sha256;
5. checks the docs' links (no version in them: they link `releases/latest`), assembles the fragments into
   `docs/releases/vX.Y.Z.md` and commits it with the fragments removed;
6. asks before publishing, then stops with the commands for the release pull request (`main` is protected: the tool
   pushes nothing to it).

After the merge, `tools/release.py X.Y.Z --after-merge` checks that `main` is that commit's tree and its build the
one tested, waits for CI, tags, waits for the release workflow and checks that the published `.fwsc` is byte for byte
the one tested (as `frodhes-X.Y.Z.fwsc` and as the stable `frodhes.fwsc`), and checks the live emulator.

The release workflow publishes the emulator itself. It builds it from the tag and runs its selftest before anything
is published, creates the release as a draft, deploys the emulator to the `gh-pages` branch, waits until GitHub Pages
serves it, and only then publishes the release, so both appear at the same moment.

`--dry-run` runs the local checks only, shows the assembled notes and stops before anything is pushed.
`--verify-only [X.Y.Z]` re-checks a published release (the verify step alone, read-only).

## Developer MIDI CCs

These CCs are for testing and development. They are listed in the manual's CC table too; here is what each does in
full.

| CC | What it does |
| --- | --- |
| 2 | The screen's colour candidate, for choosing on the FM-1: 0 = A black (the default), 1 = B dim outline, 2 (or more) = C model-matched; not saved |
| 3 | A colour test pattern on the screen (≥ 64; < 64 back to the page), to calibrate screenshots against the panel |
| 4 | Battery query: replies CC 4 / 5 = the reading (value / 8, value mod 8); CC 6 = the segments shown, 4 = USB power |
| 8 | A simulated battery reading (value × 8; 0 = the real one) |
| 9 | The bar instruments' mode cap, VIBES and MARIMBA (0 = automatic, 1–49 = 0–48 upper modes, ≥ 50 = none; not saved) |
| 10 | Reset (≥ 64): every LFO, the delay / reverb lines and the noise to their start state (for comparing recordings) |
| 11 | The cards' design, for comparing on the FM-1 (not saved): 3 = the normal look (faders, selector blocks, switch lights); 0 = the rows before the design pass (a choice written large, no fill), 1 = a fill on every card, 2 = a thin meter line under each row, 4 = selectors as small pips under the value, 5 (or more) = a switch lights its whole card |
| 24 | Reserved: accepted and saved, no effect yet |
| 41 / 42 | Key velocity (not saved): 41 sets the key converter's test mode (0 normal, 1 off, 2 stress, 4 self-test; 8 / 9 every press's reading out on CC 33–36, on / off); 42 asks for its counters (replies on CC 38–40). `tools/hil_keyvel.py` and `tools/hil_cpu.py --keyadc` use them |
| 116 | CPU load and USB audio health query. Replies on CC 115–118; 112 / 113, the bar instruments': the lowest mode cap / the most live upper modes; 107–110, the whole audio interrupt and its tail after the sound; 100–102, the USB audio counters since the last query: underruns, missed packets, overruns, rate adjustments, the ring's fill and its low point, the audio interrupt's spacing, the stream's state; the longest stretch a flash write held the interrupts off, the flash part's suspends, the longest erase. `tools/hil_cpu.py` reads them |
| 119 | Raw voice (≥ 64 bypasses every effect and the limiter; FX does not undo it) |

The SETUP page's bottom line shows the audio engine's time per block, in µs. It must stay under 5800 µs (one block
of 256 frames). The release gate is 4500 µs for the whole audio interrupt, every voice struck with every effect on.
The release build's measured worst case (`tools/hil_cpu.py --worst`, the EQ's three bands running): Rhodes 4416 µs,
VIBES 4420 µs, MARIMBA 4436 µs.

## Changes to the Dinghy platform

Frodhes is built on Dinghy 0.4. Dinghy stays the `upstream` remote: `git fetch upstream && git merge upstream/main`.
Frodhes changes its platform files in a few small places:

- **Flash.** The flash allow-list is Frodhes' own, tighter than Dinghy's: `APP_FL_RANGE` in `frodhes_store.h`
  replaces `store.h`'s blobs and slots (`store.h`'s `NBLOB` / `NSLOT` are set by the app to 0 / 0). It allows only
  the update staging and the store:
  - the record (the settings and the user presets) in two sectors, A 0xFC000 and B 0xFD000 (`set_store.c`; a save
    writes the one the load would not pick);
  - the pattern at 0xFE000, in no region of the stock firmware's table;
  - on the SMK-37, 0xEB000..0xF3FFF: the record, the pattern and the staging;
  - 0.9.5's places are read once, by the migration, and never written.
- `store.h` finds `fm1_flash_map.h` by a relative path (the host builds have no `-Ifirmware/hal`).
- **Audio.**
  - The app may drive the codec to full scale (`APP_OUT_SHIFT`) and send the USB audio before the MASTER knob
    (`usb_pre_master`). The MASTER knob reading is smoothed.
  - The audio interrupt times itself whole and reads the USB ring's low point (`isr_stats` in `platform.c`, for the
    CC 116 query).
  - The audio interrupt's tail is one pass per 32 frames (MASTER, the clip, the USB tap, the codec's shift). A new
    MASTER ramps over the block (`master_ramp`); the headphone jack keeps MASTER's product at 24 bits
    (`MASTER_JACK_SH`). It skips the clear before `app_audio` (`APP_OUT_WRITTEN`: Frodhes writes every sample).
  - A developer build times the timer tick too (`APP_DEFS=-DFM1_PROF_TICK`: `tick_prof` in `platform.c`, the
    `tools/hil_cpu.py --tick` items; the normal build is unchanged).
- **MIDI.**
  - The TRS MIDI input can be switched off (`uart_midi_on` in `midi_uart.c`, the MIDI page's TRS IN).
  - The MIDI clock and transport packets carry their arrival time (16 bits of `fm1_ms` in their free data bytes, in
    `usb.c` and `midi_uart.c`, for the tempo). `usb.c` also takes them with the code index 5 that some hosts send.
  - The timer counts its 2 kHz phase without a divide (`sub` in `fm1_timer5_irq`), latches the TRS DMA on every 2 kHz
    call and drains the ring only when it holds a byte (`uart_midi_tick` in `midi_uart.c`).
- **USB audio.**
  - The 48 kHz resampler's overshoot above 24576 is softened before its clamp (`UAC_KNEE`), and its 12 taps are
    unrolled on 64-bit sums (`uac_tap48` in `usb.c`, the same stream).
  - The USB audio ring keeps one more block in hand (`UA_HOLD`, `UA_N` 1024 in `usb.c`): a render of up to a whole
    block can no longer run it dry and repeat a frame. This adds 5.8 ms of USB latency.
- **The second core (a build switch, off by default).** `tools/build.py --c1` (`FR_C1` in `frodhes.c`) builds a
  two-core FM-1 image: `hal/fm1_core1.h` starts core 1 at boot through `APP_EARLY()` in `platform.c` (before the audio
  and the timers), holds it on every reset (`FM1_RESET_HOOK` in `hal/fm1_sys.h`) and on a fault of core 0
  (`FM1_FAULT_HOOK` in `hal/fm1_irq.h`); both hooks are empty in every other build. `app.ld` keeps the crash record
  first in NOINIT, where core 1's stack lives. The default image is byte-identical with or without this code.
  The two-core image runs at 128-frame interrupts (`FR_C1_LAT` in `frodhes.c`): `platform.c` takes `HALF_FRAMES`
  from the app when it sets it (its own 256 otherwise; the USB ring's band follows it), and core 1 may still run
  effects code from the flash after an interrupt, so `hal/fm1_flash.h` calls the app's `FL_XIP_OFF_WAIT()` before
  each moment the flash leaves XIP (empty by default), `st_read` in `platform.c` too, and `platform.c` leaves
  `FL_SLICE_OK` to the app when it defines one.
- **The browser and the host.** It builds for the browser (`DINGHY_WEB`), and there is a host-mode fix in `gfx.c`.
- **The screen.** `FONT_S` in `gen/felucca_font.h` stores only the glyphs the firmware draws (`tools/gen_font.py`;
  the others point at `?`, which `gfx.c` draws for them).
- **The panel.**
  - The panel scan has two hooks for key velocity (`FM1_INPUT_ADC_TAKE` / `FM1_INPUT_ADC_START` in
    `hal/fm1_input.h`).
  - Its tick does less work: the 595 shift unrolled, the glow's wait its own loop, and a column whose key rows have
    not changed since a pass that left no count running skips its debounce pass (`fm1__kpass`). The four LED lines
    are set as two port words. The 595 chain moves on by one bit on 10 ticks of 11, and column 2's word is shifted in
    after column 1's lines are lit unless a key conversion runs (`fm1__sr_at`, `FM1_INPUT_ADC_BUSY`).
  - `hal/fm1_adc.h` converts without blocking and gives MASTER and the battery their own slots in the scan.
  - The new `hal/fm1_keyadc.h` reads the key rows (which row, the drive, the LED blanking, a self-test).
  - The SMK-37's button LEDs can be dimmed (`smk_led_dark` in `hal/smk_input.h`, for DISPLAY BRIGHTNESS).
- The new `hal/fm1_keep.h` holds one compiler hint for the phaser (`HAL_KEEP_REG`, an empty asm).
- **Flash writes.** The app's flash erases and page programs run in slices of about 0.25 ms with the interrupts off,
  the part suspended (75h / 7Ah) while the interrupts run between them, with the old blocking wait for a part that
  does not suspend (`fl_split_op` in `hal/fm1_flash.h`). Its CPU instructions are behind macros, so
  `tests/flash_split_test.c` runs it on a host model of the part. The update loader keeps the blocking driver. The
  same runs without the wait (`fl_op_start` / `fl_op_poll`, `settings_save_start` / `settings_save_poll` in
  `platform.c`): the settings' auto save does one slice a main-loop pass, so MIDI is never held up by it.
- **The USB names.**
  - The USB product string names the model: "Frodhes FM-1", or "Frodhes " `SMK_MODEL` on the SMK-37 (`USB_PRODUCT`,
    written into `STR2` in RAM at the first request, in `usb.c`: the MIDI port and the audio input). The update mode
    keeps "Felucca Update". The MIDI jacks carry that name (`MS_IJACK`).
  - Each model has its own USB product id (`FELUCCA_USB_PID`): FM-1 0x0006, SMK-37 Pro 0x0007, Elite 0x0008, MKE-P37
    0x0009 (`tools/build.py MODEL_PID`). These are the next free test ids after Dinghy's 0x0001, the update loader's
    0x0002 (unchanged) and 0x0005, which named the app "Frodhes" in 0.9.5 and 0.9.6. A Mac keeps a MIDI device per
    vendor / product id with the name it saw first, so a new id is what makes a new name show. A port name with the
    model in it is what the community flasher looks for.
- **The package.** The package identity stays `FM-1_958` (`tools/build.py PRODUCT`). The update loader's screen says
  FRODHES (`SCREEN_NAME`) and draws no site name at its foot (`LDR_FOOT`, a define in `ldr_screen.c`; Dinghy's screen
  shows its hub's address there).
